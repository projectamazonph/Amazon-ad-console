# v3.3 → Next.js/Prisma Port Analysis

**Recommendation up front:** v3.3 has three genuinely better ideas than anything in the current rebuild plan — Guided Drills, Integrity Center self-heal, and a real Trainer role/dashboard. Everything else it does, the rebuild already covers (often more granularly, since v3.3's object model flattens Keyword/ProductTarget/AudienceTarget into one generic `Target`). Port the three big ideas, lift the written curriculum/drill content verbatim (it's good and already done), then retire the repo.

---

## 1. The big idea worth porting: Guided Drills (click-coaching, not just end-state checks)

This is sharper than the rebuild's current Scenario Mode. Today's spec (`ScenarioCheck`) only validates the *resulting database state* — a trainee could get there by ten wrong clicks and it'd still pass. v3.3's drills score the **path**, not just the destination: highlight the one correct next element, block any other click, count mistakes and skips, score out of 100 (−12 per wrong click, −8 per skip).

### New Prisma models needed
```prisma
model NavigationDrill {
  id          String   @id @default(uuid())
  title       String
  difficulty  ScenarioDifficulty
  estimatedMinutes Int
  summary     String
  routeSteps  NavigationStep[]
}

model NavigationStep {
  id              String   @id @default(uuid())
  drill           NavigationDrill @relation(fields: [drillId], references: [id])
  drillId         String
  order           Int
  label           String
  instruction     String
  expectedSelector String   // CSS selector or data-testid of the correct element
  allowSelectors  String[]  // e.g. input fields needed before the main click
  coachHint       String
}

model NavigationDrillRun {
  id          String   @id @default(uuid())
  trainee     TraineeAccount @relation(fields: [traineeId], references: [id])
  traineeId   String
  drill       NavigationDrill @relation(fields: [drillId], references: [id])
  drillId     String
  currentStepOrder Int @default(0)
  mistakes    Int @default(0)
  skips       Int @default(0)
  score       Int?
  startedAt   DateTime @default(now())
  completedAt DateTime?
  mistakeLog  Json?    // [{stepOrder, clickedSelector, timestamp}]
}
```

### Frontend mechanism
- Every interactive element in the rebuild needs a stable `data-drill-target` attribute (selector-based, matching v3.3's pattern) — add this as a build convention now, in `ppc-simulator-ui-ux-spec.md` §12, so it doesn't get retrofitted later across every component.
- A global "drill overlay" component: when a `NavigationDrillRun` is active, it (a) renders an orange outline around the element matching `currentStep.expectedSelector`, (b) intercepts click events app-wide via a capture-phase listener, (c) allows clicks only on the expected selector or the `allowSelectors` list, (d) on wrong click: `preventDefault`, show a toast, increment `mistakes`, log it.
- This is a genuinely different engineering pattern from the rest of the app (global click interception) — build it as one shared `<DrillOverlay>` mounted at the root layout, not per-page.

## 2. Integrity Center self-heal — worth porting as its own page

v3.3 runs relationship-validation rules (orphaned ad groups, dangling targets, duplicate negatives) and offers self-heal. The rebuild's schema enforces a lot of this at the FK level already (Postgres won't let you create an orphaned `AdGroup`), so the *failure mode* is different — but the **pattern** is still valuable for two things the schema can't prevent:
- Logical inconsistencies the DB allows: a `Campaign.subtype = SB_STORE_SPOTLIGHT` whose `sellerAccount.storeSubpageCount` later drops below 3 (account state changed after campaign creation)
- Orphaned bulk-upload artifacts: rows created mid-transaction-failure during a partial bulk import bug

**Recommendation:** build a lightweight `/integrity-center` page that runs a fixed set of named validation queries (e.g. `findCampaignsWithInvalidSubtypeEligibility()`) on demand, lists violations with a one-click "Fix" (which is just a normal mutation — pause the campaign, or null out the now-invalid sub-page references) and a "Self-heal all" bulk button. This is a much smaller build than it sounds — it's just saved queries plus the same mutation routes already in `api-route-mapping.md`.

## 3. Trainer role / dashboard — this is an actual gap, not a nice-to-have

Nothing in the current schema distinguishes **trainer** from **trainee**. v3.3 has: trainer notes, trainer dashboard showing all trainees' drill/mission results, trainer log export (CSV), trainer-authored review of completed scenarios. For a real training program with multiple VAs, this isn't optional — Ryan needs to see *across* trainees, not just per-trainee scenario state.

### New Prisma additions
```prisma
enum AccountRole {
  TRAINEE
  TRAINER
  ADMIN
}

model TraineeAccount {
  // ...existing fields
  role        AccountRole @default(TRAINEE)
  trainerNotes TrainerNote[] @relation("NotesAboutTrainee")
  notesWritten TrainerNote[] @relation("NotesByTrainer")
}

model TrainerNote {
  id          String   @id @default(uuid())
  trainer     TraineeAccount @relation("NotesByTrainer", fields: [trainerId], references: [id])
  trainerId   String
  trainee     TraineeAccount @relation("NotesAboutTrainee", fields: [traineeId], references: [id])
  traineeId   String
  note        String
  createdAt   DateTime @default(now())
}
```
Trainer dashboard route: `GET /api/trainer/dashboard` → aggregates `ScenarioRun`, `NavigationDrillRun`, and `TrainerNote` across all trainees the trainer has access to. CSV export reuses the same `exceljs`/CSV utility already planned for Bulk Operations export — don't build a second CSV writer.

## 4. Change history — confirms a gap I flagged earlier, now with a concrete shape to copy

v3.3's "Structured history row" per campaign is exactly the bid-history/change-log gap I noted at the end of the schema pass. Here's the concrete model, informed by v3.3's fields:

```prisma
model ChangeHistoryRow {
  id          String   @id @default(uuid())
  campaign    Campaign @relation(fields: [campaignId], references: [id])
  campaignId  String
  changedBy   String   // traineeId
  entityType  String   // "Campaign" | "AdGroup" | "Keyword" | etc.
  entityId    String
  fieldName   String   // "budgetAmount" | "bid" | "status"
  oldValue    String
  newValue    String
  changedAt   DateTime @default(now())
}
```
Every `PATCH` route in `api-route-mapping.md` should write one of these rows alongside its main mutation — cheapest way to do this is a Prisma middleware (`$use`) that diffs before/after on update calls, rather than hand-adding a history write to every single route handler.

## 5. Randomized scenario generator — apply to `ScenarioTemplate.seedConfig`

v3.3 generates randomized starting account states rather than only hand-authored ones. The rebuild's `ScenarioTemplate.seedConfig` (JSON field) already supports this — just means the seed isn't always a fixed object, it can be a generator function keyed by difficulty (e.g. randomize which products are out of stock, randomize starting budget-limited campaigns). No schema change needed, just a note for whoever implements the seeding logic: don't hardcode every scenario's starting state, write a few parameterized generators.

## 7. What v3.3 has that the rebuild deliberately does NOT need to match
- LocalStorage persistence — the rebuild uses Postgres by design (multi-trainee, trainer visibility); don't port this constraint
- Single-file architecture — the rebuild is intentionally a real app; no action needed
- "No external dependencies" — the rebuild uses shadcn/Recharts/etc. on purpose for build speed; not a regression

---

## 8. Suggested build-order insertion point
Given the current rebuild priority (Campaign Manager home → Bulk Ops → Search Term harvesting), I'd slot these in as:
1. **Change history** — do this early; it's a Prisma middleware, touches everything, and is much cheaper to add now than after 40 routes exist without it
2. **Trainer role + dashboard** — needed as soon as more than one trainee uses the tool, so before wide rollout, not necessarily before the first working demo
3. **Guided Drills** — the single highest-training-value addition, but the most engineering-novel (global click interception) — good candidate for its own dedicated build phase once core CRUD screens are stable
4. **Integrity Center** — lowest priority; nice-to-have polish once real usage surfaces actual data-inconsistency patterns worth checking for
